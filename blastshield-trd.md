# BlastShield — Technical Requirements Document

**Product:** BlastShield — AI Pre-Execution Impact Analysis for TrueForge Agents
**Version:** 1.0 (Hackathon MVP)
**Status:** Draft for implementation
**Delivery window:** 4 days
**Owner:** Engineering team (1–3 people)

> **Positioning statement:** Before a dangerous AI-agent action reaches production, BlastShield proves what that action will actually do.
> *Know the damage before the agent does it.*

### 1.1 Terminology

| Term | Definition |
|---|---|
| **Action** | A database mutation proposed by the agent. |
| **Blast radius** | The full set of rows affected by an action, including cascaded and dependent rows. |
| **Direct rows** | Rows removed or modified in the target table itself. |
| **Indirect rows** | Rows affected in dependent tables via FK cascade or dependency relationships. |
| **Analysis** | A persisted record of one interception, simulation, and risk evaluation. |
| **Sandbox** | An isolated PostgreSQL database restored from a production snapshot. |
| **Revalidation** | Re-running impact measurement immediately before production execution to detect stale approvals. |

## 2. Problem Statement

AI agents with production database credentials can execute destructive SQL that is syntactically valid, semantically plausible, and catastrophically wrong. Existing approval systems answer the question *"Is this agent permitted to run this SQL?"* — a permissions question. They do not answer *"What will happen if I approve this?"* — a consequence question.

A human approving `DELETE FROM users WHERE last_login < NOW() - INTERVAL '2 years'` has no visibility into:

- how many rows actually match the predicate,
- which dependent tables cascade,
- how many paying customers are inside that set,
- how much recurring revenue is destroyed,
- whether the operation is reversible.

BlastShield closes that gap by simulating the action against a restored production snapshot and returning evidence rather than an opinion.

---

## 3. Goals and Non-Goals

### 3.1 Goals (MVP)

- **G1.** Intercept all destructive SQL generated by a TrueForge agent before it reaches production.
- **G2.** Execute the proposed SQL safely in an isolated sandbox restored from a production snapshot.
- **G3.** Measure real before/after row counts across the target table and its dependents.
- **G4.** Translate row counts into business impact (active subscriptions, MRR, ARR at risk).
- **G5.** Produce a deterministic risk score and level.
- **G6.** Generate and analyze a safer alternative operation.
- **G7.** Require explicit human approval before any production mutation.
- **G8.** Revalidate production state at execution time and reject stale approvals.
- **G9.** Record a complete audit trail of every step.

### 3.2 Non-Goals (explicitly out of scope for the 4-day build)

| Excluded | Reason |
|---|---|
| AWS / Kubernetes / Gmail / GitHub integrations | Not required to prove the core thesis |
| Multiple database engines | PostgreSQL only |
| Full authentication system | Single-session demo |
| Multi-tenant SaaS | Single workspace |
| Production-grade replication | Snapshot + restore is sufficient |
| ML-based risk model | Deterministic scoring is more defensible |
| Universal SQL coverage | DELETE/UPDATE/TRUNCATE/DROP only |

These belong on the **Future Roadmap**, not in the MVP.

### 3.3 Operating Principle

> **The LLM proposes. The deterministic backend verifies. The human authorizes. The execution layer enforces.**

The safety boundary must come from actual database inspection and simulation — never from asking the same LLM that generated the dangerous operation whether that operation is safe.

## 4. Scope

### 4.1 Supported Operations

| Operation | Classification | MVP support |
|---|---|---|
| `SELECT` | SAFE | Pass-through, no analysis |
| `EXPLAIN` | SAFE | Pass-through |
| `INSERT` | MEDIUM | Classified, minimal analysis |
| `UPDATE` | POTENTIALLY DANGEROUS | Full analysis |
| `DELETE` | HIGH RISK | **Full analysis — primary demo path** |
| `TRUNCATE` | CRITICAL | Full analysis |
| `DROP TABLE` | CRITICAL | Full analysis |

`DELETE` on the `users` table is the reference implementation and must be the most polished path.

### 4.2 Reduced Scope (solo builder)

If the project is built by one person, reduce to:

- `DELETE` only
- `users` as the only root table
- 4 dependent tables
- One safer alternative (soft delete)
- One demo prompt

Working depth beats broken breadth.

## 7. Demo Database Requirements

### 7.1 Schema

A realistic fake SaaS production database.

```
users
 ├── subscriptions
 ├── orders
 │    └── payments
 ├── invoices
 └── sessions
```

| Table | Columns |
|---|---|
| `users` | `id`, `name`, `email`, `status`, `last_login`, `created_at`, `deleted_at` |
| `subscriptions` | `id`, `user_id`, `status`, `monthly_price`, `started_at` |
| `orders` | `id`, `user_id`, `amount`, `status`, `created_at` |
| `payments` | `id`, `order_id`, `amount`, `status` |
| `invoices` | `id`, `user_id`, `amount`, `status` |
| `sessions` | `id`, `user_id`, `last_active` |

### 7.2 Seed Volume

| Table | Target rows |
|---|---|
| `users` | 50,000 |
| `orders` | 100,000 |
| `subscriptions` | 15,000 |
| `payments` | 90,000 |
| `invoices` | 30,000 |
| `sessions` | 120,000 |

**Requirement:** Volumes must be large enough that the blast radius is visually striking in the UI.

### 7.3 Foreign Key Requirements

- At least three relationships must use `ON DELETE CASCADE` so that hidden consequences are real, not simulated.
- The dependency chain must be at least two levels deep (`users → orders → payments`) to demonstrate transitive impact.
- The seed must be deterministic so that repeated demo runs produce identical numbers.

**Reference outcome:** deleting 12,481 users must not report "12,481 rows affected" — it must report the full cascade (≈21,003 orders, 18,201 payments, 347 subscriptions, 5,102 invoices, 9,682 sessions).

## 8. Agent Requirements

### 8.1 Agent Definition

One agent: **BlastShield Database Operator**.

Responsibilities:

1. Interpret the user's natural-language request.
2. Generate the corresponding SQL.
3. Route any destructive SQL through `request_database_change()`.
4. Never execute destructive SQL directly.
5. Present the resulting risk report to the user.

### 8.2 Tool Exposure Constraint

**REQ-AGENT-1 (P0):** The agent must not be given any tool capable of arbitrary SQL execution. A tool such as `run_any_sql(sql)` must not exist in the agent's tool surface. Bypass capability invalidates the entire safety model.

---

## 9. MCP Server Requirements

The custom PostgreSQL MCP server exposes exactly four tools.

### 9.1 `get_schema()`

Returns the production schema:

- tables
- columns and types
- primary keys
- foreign keys
- constraints
- cascade rules

### 9.2 `run_read_query(sql)`

| Allowed | Blocked |
|---|---|
| `SELECT`, `EXPLAIN` | `DELETE`, `UPDATE`, `DROP`, `TRUNCATE`, `ALTER`, `INSERT` |

**REQ-MCP-1 (P0):** Blocking must be enforced by parsing the statement, not by string matching. Any statement that does not parse to a read-only operation is rejected.

### 9.3 `request_database_change(sql)`

The core interception tool. It **must not execute** the SQL.

```json
{
  "analysis_id": "abc123",
  "status": "requires_review"
}
```

On receipt, BlastShield begins asynchronous analysis.

### 9.4 `execute_approved_change(analysis_id)`

**REQ-MCP-2 (P0):** Execution proceeds only when `analysis.status == APPROVED`. Any other status returns `Execution denied.` This check happens server-side and is not influenced by agent input beyond the `analysis_id`.

## 10. Backend Service Requirements

### 10.1 SQL Parser (`sql_parser.py`)

**REQ-PARSE-1 (P0):** Use `sqlglot` as the primary parser. Regex must not be used as the primary parsing mechanism.

Input:
```sql
DELETE FROM users WHERE last_login < NOW() - INTERVAL '2 years';
```

Output:
```json
{
  "operation": "DELETE",
  "table": "users",
  "condition": "last_login < NOW() - INTERVAL '2 years'",
  "dangerous": true
}
```

### 10.2 Action Classifier

**REQ-CLASS-1 (P0):** Classification is deterministic backend code. The LLM is never asked whether an operation is dangerous.

| Operation | Level |
|---|---|
| `SELECT` | SAFE |
| `INSERT` | MEDIUM |
| `UPDATE` | POTENTIALLY DANGEROUS |
| `DELETE` | HIGH RISK |
| `TRUNCATE` | CRITICAL |
| `DROP` | CRITICAL |

### 10.3 Sandbox Manager (`sandbox_manager.py`)

Two databases, both running in PostgreSQL under Docker:

- `blastshield_prod`
- `blastshield_sandbox`

**Initial setup:**
```
Seed production → create clean snapshot → restore snapshot into sandbox
```

**Per-analysis lifecycle:**
```
Reset sandbox → restore clean state → execute proposed SQL → measure results
```

Implementation may use `pg_dump` + `pg_restore`, or a deterministic seed script.

**REQ-SANDBOX-1 (P0):** Destructive SQL is executed only against the sandbox during analysis. No analysis path may write to production.
**REQ-SANDBOX-2 (P0):** Sandbox reset must be reliable and repeatable across at least 10 consecutive demo runs. Reliability outweighs replication sophistication.

### 10.4 Impact Analyzer (`impact_analyzer.py`)

**Before/after simulation (P0):**

| Table | Before | After | Difference |
|---|---|---|---|
| `users` | 50,000 | 37,519 | 12,481 |
| `orders` | 100,000 | 78,997 | 21,003 |
| `subscriptions` | 15,000 | 14,653 | 347 |

Row counts are captured before execution, the SQL is run in the sandbox, counts are captured again, and the deltas are recorded per table.

### 10.5 Dependency Analyzer (`schema_analyzer.py`)

Query PostgreSQL system catalogs to discover:

- foreign keys
- `ON DELETE CASCADE`
- `ON UPDATE CASCADE`
- dependent tables

Build the dependency tree:

```
users
├── subscriptions
├── orders
│   └── payments
├── invoices
└── sessions
```

**REQ-DEP-1:** Recursive traversal is limited to **2–3 levels**. Arbitrary enterprise-scale graph traversal is out of scope.

### 10.6 Business Impact Analyzer

This is the feature that elevates the output above "12,481 rows affected."

```sql
SELECT COUNT(*) FROM subscriptions
WHERE status = 'active' AND user_id IN (...);
-- → 347 active subscriptions affected

SELECT SUM(monthly_price) FROM subscriptions
WHERE status = 'active' AND user_id IN (...);
-- → MRR at risk: $6,116
-- → ARR at risk: $73,392
```

**Required output surface:**
- *347 paying customers affected*
- *$73.4K estimated ARR at risk*

### 10.7 Risk Engine (`risk_engine.py`)

**REQ-RISK-1 (P0):** Scoring is fully deterministic. No AI model participates in scoring.

| Factor | Max points |
|---|---|
| Operation severity | 25 |
| Rows affected | 25 |
| Cascade impact | 20 |
| Business-critical data | 20 |
| Reversibility | 10 |
| **Total** | **100** |

Worked example:

| Factor | Value | Score |
|---|---|---|
| Operation | DELETE | 20 |
| Rows affected | 12,481 users | 22 |
| Cascades | 3 | 15 |
| Business-critical | 347 active subscriptions | 20 |
| Reversibility | Hard rollback | 8 |
| **Total** | | **85 — CRITICAL** |

| Range | Level |
|---|---|
| 0–24 | LOW |
| 25–49 | MEDIUM |
| 50–74 | HIGH |
| 75–100 | CRITICAL |

### 10.8 Safer Alternative Generator

Original:
```sql
DELETE FROM users WHERE last_login < NOW() - INTERVAL '2 years';
```

Safer:
```sql
UPDATE users SET deleted_at = NOW()
WHERE last_login < NOW() - INTERVAL '2 years';
```

**REQ-ALT-1 (P0):** The generated alternative must itself be run through the full analysis pipeline. Its risk score must be measured, not asserted.

Expected comparison:

| | Original | Recommended |
|---|---|---|
| Risk | 85 (CRITICAL) | 34 (MEDIUM) |
| Affected records | 48,615 | 12,481 |
| Cascading deletions | 3 | 0 |
| Rollback | Difficult | Easy |

### 10.9 Production Revalidation (`execution_service.py`)

Between approval and execution, production data may change.

```
Approved:  12,481 users
Current:   12,912 users
→ ⚠ PRODUCTION STATE CHANGED · approval invalidated · re-analysis required
```

MVP implementation:

```python
if current_affected_rows != approved_affected_rows:
    reject_execution()
```

**REQ-REVAL-1 (P1):** A basic equality check is sufficient for the MVP. Threshold-based tolerance is a future enhancement.

## 11. Data Model

### 11.1 `analyses`

| Column | Notes |
|---|---|
| `id` | Primary key |
| `session_id` | Groups analyses in one agent session |
| `original_sql` | As proposed by the agent |
| `operation_type` | DELETE / UPDATE / TRUNCATE / DROP |
| `target_table` | Root table |
| `risk_score` | 0–100 |
| `risk_level` | LOW / MEDIUM / HIGH / CRITICAL |
| `direct_rows` | Rows in target table |
| `indirect_rows` | Sum of dependent rows |
| `status` | See state machine below |
| `safer_sql` | Generated alternative |
| `created_at`, `approved_at`, `executed_at` | Timestamps |

### 11.2 Status State Machine

```
ANALYZING → WAITING_APPROVAL → APPROVED → EXECUTED
                  │                │
                  ▼                ▼
              REJECTED        INVALIDATED
```

| Status | Meaning |
|---|---|
| `ANALYZING` | Simulation in progress |
| `WAITING_APPROVAL` | Risk report ready, awaiting human |
| `APPROVED` | Human authorized execution |
| `REJECTED` | Human cancelled |
| `EXECUTED` | Applied to production |
| `INVALIDATED` | Revalidation detected production drift |

### 11.3 `impact_items`

| Column | Example |
|---|---|
| `id` | — |
| `analysis_id` | FK |
| `table_name` | `orders` |
| `relationship` | `CASCADE` |
| `affected_rows` | `21003` |
| `impact_type` | `DEPENDENT` |

### 11.4 `audit_events`

| Column | Notes |
|---|---|
| `id`, `analysis_id`, `event_type`, `payload`, `created_at` | — |

Event types: `ACTION_INTERCEPTED`, `SANDBOX_CREATED`, `SIMULATION_COMPLETED`, `RISK_CALCULATED`, `USER_APPROVED`, `EXECUTION_STARTED`, `EXECUTION_COMPLETED`.

## 12. API Specification

Five endpoints. No more are required.

### 12.1 Start analysis

```
POST /api/analysis
```
```json
{ "sql": "DELETE FROM users WHERE last_login < NOW() - INTERVAL '2 years'" }
```
```json
{ "analysis_id": "abc123" }
```

### 12.2 Get analysis

```
GET /api/analysis/{id}
```
```json
{
  "risk": 85,
  "level": "critical",
  "direct_rows": 12481,
  "indirect_rows": 36134,
  "active_subscriptions": 347,
  "arr_at_risk": 73392,
  "safer_sql": "UPDATE users SET deleted_at = NOW() WHERE ...",
  "status": "WAITING_APPROVAL"
}
```

### 12.3 Approve

```
POST /api/analysis/{id}/approve
```

### 12.4 Execute

```
POST /api/analysis/{id}/execute
```

Execution sequence: **revalidate → compare → execute if unchanged, otherwise invalidate.**

### 12.5 Audit trail

```
GET /api/analysis/{id}/events
```

## 15. Reference User Journey

The single scenario the MVP must perform perfectly:

1. User: *"Delete inactive customers older than 2 years."*
2. TrueForge generates `DELETE FROM users WHERE last_login < NOW() - INTERVAL '2 years'`.
3. BlastShield intercepts.
4. Sandbox resets and restores.
5. SQL executes safely in sandbox.
6. Impact is measured.
7. Risk report renders.
8. User sees: 12,481 users · 347 paying customers · 48K total records · $73K ARR at risk.
9. BlastShield proposes soft delete.
10. User selects the safer version.
11. BlastShield re-analyzes.
12. Risk drops 85 → 34.
13. User approves.
14. Production is revalidated.
15. The safe operation executes.

**REQ-DEMO-1:** Do not build five demo scenarios. Perfect this one.

## 20. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Sandbox restore is slow or flaky | Demo stalls mid-analysis | Deterministic seed script as fallback to `pg_dump`/`pg_restore`; pre-warm before demo |
| Agent produces unparseable SQL | Interception fails | Constrain agent prompt to the demo scenario; fail closed — unparseable SQL is treated as dangerous |
| LLM/API/network failure during demo | No live demo | Pre-recorded screen capture as fallback |
| Dependency traversal explodes | Analysis hangs | Hard 2–3 level depth cap |
| Scope creep into P2 features | P0 breaks unnoticed | Enforce the P0 stop rule |
| Frontend built against mock data | Judges see hardcoded numbers | Day 3 afternoon wiring is a gate, not a task |
